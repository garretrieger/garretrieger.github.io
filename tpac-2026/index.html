IFT Encoding Model Recap

An IFT-encoded font starts with a compact Initial Font (WOFF2) containing baseline coverage and patch mapping tables (IFT / IFTX).

Clients dynamically extend the font by fetching two distinct types of patches:

  • Outline Data: glyf, loca, gvar, CFF, CFF2
  • Non-Outline Data: cmap, GSUB, GPOS, COLR, metrics, etc.

Two Complementary Patch Types

  • Glyph-Keyed Patches (.ift_gk)
    Extend outline tables. Keyed by glyph IDs; independent and additive—any combination can be applied in any order in a single round trip.
  • Table-Keyed Patches (.ift_tk)
    Extend non-outline tables via per-table Brotli shared-dictionary binary diffs. Invalidating—each patch transitions the font from a specific base state to a new extended state in a directed graph.
  • Mixed Mode (Encoder Default)
    Combines both: table-keyed patches coarse-grain non-outline tables (e.g., per script), while glyph-keyed patches fine-grain outline data.

Before diving into the encoder internals, let's briefly recap what the encoder produces. An IFT encoding splits font data into outline tables and non-outline tables. Outline tables are extended via Glyph-Keyed patches, which are additive per-glyph bundles. Non-outline tables are extended via Table-Keyed patches, which are binary diffs relative to a specific base font state. The encoder operates in Mixed Mode by default, combining coarse table-keyed patches with fine-grained glyph-keyed patches.

Overview: Three-Stage Encoding Pipeline

  • Clean Separation of Concerns: Stages 1 & 2 make all high-level policy and optimization decisions; Stage 3 is a deterministic low-level compiler that executes the SegmentationPlan.
  • Inspectable Protobuf Contracts: Intermediate artifacts are human-readable textprotos (segmenter_config.proto and segmentation_plan.proto).

Under the hood, IFT font encoding happens in three distinct stages separated by clean protobuf schemas. Stage 1 analyzes the font and builds a SegmenterConfig. Stage 2 runs the dependency graph analyzer and cost-based merger to produce a SegmentationPlan. Stage 3 compiles the plan and original font into the final WOFF2 initial font and patch files.

Producing IFT Fonts: Single-Step Auto Config

The simplest way to encode an IFT font is //util:font2ift, which runs all three stages automatically with zero required configuration:

bazel run -c opt //util:font2ift -- \
  --input_font="$HOME/myfont/MyFont.ttf" \
  --output_path="$HOME/myfont/ift/" \
  --output_font="MyFont-IFT.woff2"

--auto_config_primary_script

Specifies the primary script or language the font is deployed for (values from w3c/ift-encoder-data, e.g., Script_japanese, Script_bengali, Language_fr):

  • Enables primary script codepoints to merge into the initial font.
  • Splits overlapping script clusters (e.g. CJK) to prioritize the primary script's frequency distribution.

--auto_config_quality

Analogous to a compression library quality level (1 to 7):

  • Controls how much CPU effort is spent optimizing the segmentation.
  • Higher values increase encoding time but reduce average bytes transferred by clients.
  • Automatically selected by heuristic if omitted.

For most users, font2ift provides a single-command workflow. You give it an input font and output path, and it automatically generates a config, segments the font, and compiles the output. Two optional flags let you guide auto-configuration: --auto_config_primary_script and --auto_config_quality.

Producing IFT Fonts: Multi-Step Advanced Workflow

When fine-grained control or custom experimentation is needed, each stage can be invoked individually and hand-tuned:

Step 1: Segmenter Config

bazel run -c opt \
  //util:gen_ift_segmenter_config -- \
  --quality=5 \
  --input_font=MyFont.ttf \
  > config.txtpb

Or hand-author using segmenter_config.proto (custom merge groups, custom Riegeli frequency files, custom thresholds).

Step 2: Segmentation Plan

bazel run -c opt \
  //util:gen_ift_segmentation_plan -- \
  --input_font=MyFont.ttf \
  --config=config.txtpb \
  > plan.txtpb

Generates glyph-keyed patches, CNF conditions, and optional table-keyed segments (or combine with gen_ift_table_keyed_plan).

Step 3: Compile IFT Font

bazel run -c opt \
  //util:font2ift -- \
  --input_font=MyFont.ttf \
  --plan=plan.txtpb \
  --output_path=out/ \
  --output_font=MyFont.ift.woff2

Executes plan.txtpb to emit the initial WOFF2 font and all .ift_gk / .ift_tk patches.

For advanced use cases—such as inspecting intermediate plans, supplying custom frequency datasets, or tuning merge parameters—each stage has its own CLI utility: gen_ift_segmenter_config, gen_ift_segmentation_plan, and finally font2ift --plan=....

Part 1: Automatic Configuration

Script detection, overlap clustering, quality levels & heuristics

Let's now dive into Part 1: how AutoSegmenterConfig analyzes an input font and constructs an effective segmentation configuration automatically.

What AutoSegmenterConfig Does

Given only an input hb_face_t* (plus optional primary_script and quality_level), AutoSegmenterConfig::GenerateConfig synthesizes a complete SegmenterConfig:

  1. Script Detection: Intersects font codepoints against built-in frequency datasets from w3c/ift-encoder-data (183 logical script & language datasets).
  2. Overlap Clustering: Groups scripts that share a significant fraction of their unigram probability mass into unified MergeGroups.
  3. Primary Script Prioritization: Enables initial-font merging for the primary script (defaulting to Script_latin) and isolates it from overlapping secondary scripts.
  4. Table-Keyed Graph Setup: Configures FROM_FREQ_DATA table-keyed segments, jump_ahead = 2, use_prefetch_lists = true, and caps max_depth so total table-keyed patches stay ≤ 2048.
  5. Quality Level Selection: Applies either the user-requested quality level (1..7) or the Auto Quality Heuristic based on font codepoint count.

AutoSegmenterConfig::GenerateConfig is responsible for five key tasks: detecting which scripts are present in the font, clustering overlapping scripts into merge groups, prioritizing the primary script, bounding the table-keyed patch graph size, and configuring quality/runtime tradeoffs.

Script Detection & Overlap Clustering

1. Detecting Present Scripts

  • Computes non_cjk_common: codepoints appearing in ≥ 2 non-CJK script datasets.
  • A script is detected if the font contains > 1 codepoint unique to that script (after subtracting non_cjk_common).
  • CJK scripts (Japanese, Korean, Chinese-simplified, Chinese-traditional) share unified Han ideographs, so CJK-specific overlap is kept during detection.

2. Clustering Overlapping Scripts

  • Why cluster? Any segment present in > 1 merge group becomes a shared segment and is excluded from cost-based merging!
  • Naive intersection fails: Almost all scripts share space (U+0020) or basic punctuation.
  • Probability Mass Overlap: Filters out control/format/space & combining marks (U+0300..U+0400), then measures shared unigram probability mass using the lightweight 1.5 MB unigram dataset: max( Pi(Si ∩ Sj) / Pi(Si),  Pj(Si ∩ Sj) / Pj(Sj) )  ≥  0.10

Example (NotoSansJP): CJK scripts share > 98% probability mass → grouped into Chinese-simplified+Chinese-traditional+Japanese+Korean; Emoji/Latin/Symbols group into Emoji+Latin+Symbols; Greek and Cyrillic form separate singleton groups.

A subtle problem arises when a font supports multiple scripts: if two scripts share codepoints and are placed in separate merge groups, those shared codepoints are excluded from cost merging. Conversely, if we group any two scripts that share a single codepoint, spaces and punctuation chain every script into one giant group. Our solution is to filter out spaces, controls, and common combining marks, and then measure what fraction of each script's total unigram probability mass is covered by their shared codepoints. If that fraction is at least 10% (kScriptOverlapThreshold = 0.10), we union them into a single merge group.

Auto Config: The Auto Quality Heuristic

Current Heuristic (AutoPickQuality)

Selects a quality level based on the font's total Unicode codepoint count, calibrated across the Google Fonts corpus (~2,057 families) so that fewer than 0.5% of fonts in a bin take ≥ 10 minutes to segment:

Codepoint Count Bin Selected Quality Corpus % ≥ 10 min
[1, 300] Quality 7 0.3%
(300, 1500] Quality 6 0.3%
(1500, 3100] Quality 4 0.0%
(3100, 30000] Quality 2 0.0%
(30000, ∞) Quality 1 28.6%

Why Codepoint Count Alone Isn't Enough

  • Some smaller fonts (e.g., complex Arabic/Nastaliq or Indic fonts with deep contextual GSUB chains) have high condition complexity despite moderate codepoint counts.
  • Conversely, large multi-script fonts partitioned into many small, disjoint merge groups run much faster than a monolithic CJK group of the same total size.

Future Direction: Budget-Driven Selection

  • Accept a target encoding time budget (e.g., O(1 min), O(10 min)).
  • Sample a few Brotli & closure operations on the target font to measure per-op cost.
  • Estimate total Brotli & condition operations per merge group (incorporating condition complexity) and pick per-group quality settings to fit the budget.

When the user doesn't specify a quality flag, AutoPickQuality picks a default based on the number of codepoints in the font. We calibrated these five bins across the entire Google Fonts library so that for fonts up to 30,000 codepoints, fewer than 0.5% of runs exceed 10 minutes. In the future, we plan to evolve this into a dynamic cost-model estimator that factors in per-merge-group sizes and OpenType layout condition complexity.

Part 2: Glyph Segmentation & Dependency Graph

Mapping Unicode codepoints & features to closure-safe glyph patches

Now let's move to Part 2: how the segmenter bridges the gap between Unicode codepoints in the client's text and Glyph IDs in the font's outline tables.

The Glyph Segmentation Problem

In an IFT font, the client decides which patches to load based on the Unicode codepoints and layout features present in the document—but outline patches contain Glyph IDs (GIDs).

Why Is This Non-Trivial?

  • OpenType tables (cmap 14 UVS, GSUB ligatures, contextual/chaining substitutions, glyf composites, COLR layers) dynamically substitute or combine glyphs during shaping.
  • If glyph f is in Patch 1 and glyph i is in Patch 2, rendering "fi" loads both patches—which activates the GSUB rule f + i → fi!
  • The fi ligature glyph must be available whenever both f and i are present.

Here's the core problem of glyph segmentation: patch activation conditions are evaluated against Unicode codepoints and feature tags, whereas outline patches store Glyph IDs. Because of OpenType layout substitutions like the classic f + i -> fi ligature, placing f and i in separate patches requires a third patch for fi guarded by the conjunctive condition (f AND i).

Core Concepts & The Closure Requirement

Segment (si)

The atomic unit of extension: a disjoint set of Unicode codepoints and/or OpenType layout feature tags.

Initial Font (s0)

Baseline codepoints, features, and glyphs included directly in the initial WOFF2 font—always loaded with zero patch overhead.

Disjoint Patches

Every glyph outside s0 is placed in exactly one glyph-keyed patch. Glyphs are never duplicated across patches.

The Closure Requirement:
For any subset definition D (Unicode codepoints + feature tags), the set of glyphs loaded from the Initial Font s0 and all patches pi whose activation condition ci(D) = true must satisfy:
Glyphs(s0) ∪ ⋃ci(D) = true Glyphs(pi)  ⊇  closure(Font, D)

Satisfying the closure requirement guarantees that shaping and rendering any text covered by D on the extended IFT font produces identical output to the original unsubsetted font.

Every segmentation plan produced by our segmenter must uphold two invariants: first, glyph patches are strictly disjoint so we never waste bandwidth duplicating glyph outlines across patches; second, it must satisfy the Closure Requirement—for any combination of codepoints and features, the loaded patches must be a superset of the HarfBuzz subsetter glyph closure for that subset definition.

High-Level Segmenting Algorithm

Implemented in ClosureGlyphSegmenter::CodepointToGlyphSegments (closure_glyph_segmenter.cc):

  1. Initialize Fine-Grained Segments: Start with each Unicode codepoint and optional layout feature supported by the font as an individual segment (optionally pre-grouping low-probability tail codepoints into groups of 4).
  2. Extract Glyph Activation Conditions: Analyze intra-font dependencies with respect to the initial segments to assign every glyph a normalized boolean activation condition in terms of segments.
  3. Form Initial Patch Groupings: Group all glyphs that share an identical activation condition into an initial patch set:
    • Exclusive patches: triggered by a single segment if (s_i)
    • Conjunctive / Disjunctive / Composite patches: triggered by boolean combinations e.g. if ((s_1 OR s_2) AND s_3)
  4. Initial Font Merging: Evaluate high-probability patches and move those that reduce total expected cost (plus any unmapped fallback glyphs) into the Initial Font (s0).
  5. Iterative Cost & Heuristic Merging: Within each isolated Merge Group, iteratively merge segments and patches to minimize the expected byte cost function and satisfy minimum group sizes.

Rather than trying to guess coarse codepoint blocks upfront, our segmenter works bottom-up: we start with the finest possible segmentation (one segment per codepoint and feature), extract exact glyph activation conditions, group glyphs with identical conditions into initial patches, merge near-100% probability patches into the initial font, and then iteratively merge segments and patches guided by our expected-byte cost function.

Condition Analysis: Closure vs. Dependency Graph

The segmenter supports two mechanisms for discovering per-glyph activation conditions (ConditionAnalysisMode):

1. Subsetter Closure Analysis (CLOSURE_ONLY)

Legacy Treats hb_subset glyph closure as a black box. For each segment si:

  • A = closure(⋃all sj),  B = closure(⋃j≠i sj)
  • I = closure(s0 ∪ si) ∖ closure(s0) (activated by si)
  • D = A ∖ B (dropped when si is removed)
  • Exclusive: D ∩ I ⇒ si
  • Conjunctive: D ∖ I ⇒ si ∧ …
  • Disjunctive: I ∖ D ⇒ si ∨ …

Downsides: Requires O(n) full HarfBuzz closure invocations; misses complex multi-segment composite conditions (s1 ∧ s2) ∨ (s3 ∧ s4).

2. Dependency Graph Analysis (DEP_GRAPH_ONLY)

Recommended Default Directly extracts substitution & composition rules into a directed graph (DependencyGraph):

  • Propagates exact boolean conditions in a single phased topological pass via Tarjan's SCC algorithm.
  • Captures arbitrary composite CNF conditions (s1 ∨ s2) ∧ (s3 ∨ s4) directly without combinatorial closure probing.
  • Supports fast incremental invalidation during merging.
  • DEP_GRAPH_ONLY_WITH_SIMPLIFICATION (Q1): Simplifies composite conditions into pure disjunctive/conjunctive supersets for extreme fonts.

Originally, we inferred glyph conditions by treating HarfBuzz's subsetter closure as a black box—computing the full closure A, the closure without segment si (B), and the isolated closure of si (I). By intersecting I and D = A − B, we could classify glyphs as exclusive (D ∩ I), conjunctive (D − I), or disjunctive (I − D). However, running hundreds of full subsetter closures is slow and struggles with composite conditions. Today, our default and recommended approach is DEP_GRAPH_ONLY, which builds an explicit dependency graph directly from the font's tables.

The Closure Dependency Graph: Node Types

DependencyGraph (ift/dep_graph/dependency_graph.h) wraps the HarfBuzz dependency graph API and unifies four levels of font entities into a single directed graph:

  • Unicode Closure Edges (UnicodeEdges): Models HarfBuzz's Unicode canonical decomposition/composition and bidi mirroring edges between codepoint nodes before cmap lookup.

The DependencyGraph class unifies four types of nodes into one graph: Segment nodes act as the entry points; they point to Unicode Codepoint nodes and Feature nodes. Codepoint nodes have edges to other codepoints (modeling Unicode canonical decomposition, composition, and bidi mirroring) and to Glyph nodes via cmap and cmap 14 UVS subtables. Finally, Glyph nodes have outgoing edges to other glyphs derived from GSUB, COLR, MATH, and glyf composite references.

Dependency Graph: Edge Types & Init Font Folding

Disjunctive Edge: u → v

Unconditional dependency: if node u is present, destination node v is required (u ⇒ v).

  • Examples: Segment → Codepoint, nominal cmap mapping, glyf composite glyph → component glyph, COLR base glyph → layer glyphs, default-feature GSUB single/alternate substitution.

Initial Font Folding (s0)

All codepoints, features, and glyphs in the Initial Font are treated as already reached (True):

  • If i is in the Initial Font, the conjunctive edge f → fi (ctx: {i}) automatically simplifies into a disjunctive edge f → fi!

Conjunctive Edge: u —(context C)→ v

Conditional dependency: if source u AND all items in context C (features, codepoints, and/or glyphs) are present, then v is required.

  • Symmetric Representation: For ligatures, features, and UVS pairs, an edge is added for each member of the conjunction:
    • Ligature f + i → fi:
      f → fi with ctx = {i}
      i → fi with ctx = {f}
    • UVS a + VS1 → a.alt:
      a → a.alt with ctx = {VS1}
      VS1 → a.alt with ctx = {a}
    • Optional Feature smcp on a → a.sc:
      a → a.sc (ctx = {smcp}) & smcp → a.sc (ctx = {a})

Edges in the dependency graph come in two flavors: disjunctive edges (u → v, meaning u alone triggers v) and conjunctive edges (u → v with a context set C of required features, codepoints, or glyphs). For ligatures, UVS mappings, and feature-gated lookups, the graph stores symmetric edges from every participant. Crucially, anything already in the initial font is folded out of all context sets immediately—so if i is in the initial font, the edge f -> fi loses its {i} context requirement and becomes a simple disjunctive edge.

Dependency Graph Traversal & Closure Phasing

Two Traversal Modes

  • Enforced Context Traversal:
    A conjunctive edge u —(C)→ v is traversed only after u and every node in C have been reached. Accurately mimics HarfBuzz's subsetting closure (may slightly over-approximate on complex contextual GSUB rules).
  • Non-Enforced Context Traversal:
    Conjunctive edges are always traversed even if their context C is not met. Used to quickly find all glyphs/segments that could potentially interact with a starting node (e.g., scoping incremental invalidations).

Strict Closure Phasing

To match HarfBuzz's glyph closure semantics, graph traversal and condition extraction are executed in sequential phases, restricting active edges to the current phase:

  1. Phase 1: Segment → Unicode codepoint & Feature edges + Unicode decomposition/composition
  2. Phase 2: cmap nominal glyph mappings & cmap 14 UVS edges
  3. Phase 3: GSUB layout substitution lookups & MATH / COLR tables
  4. Phase 4: glyf composite glyph component edges

Why phase? A glyf composite component glyph does not trigger GSUB substitutions on its own—phasing prevents false transitive dependencies!

A critical subtlety of OpenType subsetting is that HarfBuzz's glyph closure is phased: for example, composite glyphs in the glyf table pull in their component glyphs *after* GSUB substitutions have finished, so a component glyph pulled in by a composite won't itself trigger new GSUB rules. Our dependency graph mirrors this exact phasing during both graph traversal and condition extraction.

Dependency Graph Condition Extraction Algorithm

Implemented in dependency_closure.cc (docs/dependency_graph_condition_extract.md). Run sequentially for each closure phase:

  1. Initialize Node Conditions:
    • All nodes in the Initial Font (s0) → True
    • Each Segment node si → ActivationCondition::exclusive_segment(s_i)
    • All other nodes → unmapped (retain conditions accumulated from earlier phases).
  2. Precompute Incoming Edges: Collect active incoming edges (p1, …, pk) → v for the current phase.
  3. Find Strongly Connected Components (SCCs): Run Tarjan's SCC algorithm, which partitions the phase subgraph into SCCs and emits them in topological order.
  4. Propagate Conditions in Topological Order:
    • Single-Node SCC (|C| = 1): For each incoming edge, join parent conditions via ActivationCondition::And(...), then join all incoming edges into node v's condition via ActivationCondition::Or(...) and normalize to CNF.
    • Multi-Node SCC (|C| > 1, cyclic GSUB rules): Iterate through nodes in the component, propagating And/Or conditions repeatedly until a fixed point is reached (no node conditions change).

How do we turn the dependency graph into boolean activation conditions for every glyph? Within each closure phase, we run Tarjan's Strongly Connected Components algorithm. Tarjan's algorithm gives us the SCCs in topological order. For any single-node SCC, we simply compute its condition once by joining its parents' conditions—using And across conjunctive edge contexts and Or across distinct incoming edges. If a font has cycles in its GSUB rules (a multi-node SCC), we iterate around the SCC until the boolean conditions reach a fixed point.

Condition Representation & Normalization

ActivationCondition (activation_condition.h) stores every condition in canonical Monotonic Conjunctive Normal Form (CNF)—a sorted vector of disjunctive SegmentSet clauses:

C  =  (s1,1 ∨ s1,2 ∨ …)Clause C1  ∧  (s2,1 ∨ s2,2 ∨ …)Clause C2  ∧  …

Subsumption Simplification (Simplify)

  • Sorts clauses by cardinality (|Ci| ascending), then removes any clause Cj that is a superset of an earlier clause Ci ⊆ Cj: (s1) ∧ (s1 ∨ s2)  ⇒  (s1)
  • Final lexicographical sort guarantees a unique canonical representation for hashing & equality (`ConditionsAndGlyphs` map).

Fast And, Or & Superset Reduction

  • And(A, B): Concatenates clauses of A and B, then runs Simplify().
  • Or(A, B) Optimization: Before taking the Cartesian cross-product of clauses, extracts identical clauses I shared by A and B in one linear scan: (I ∧ A′) ∨ (I ∧ B′)  =  I ∧ (A′ ∨ B′)
  • NonCompositeSuperset(): Drops composite clauses to keep either all unit conjunctive clauses (si ∧ sj) or the single lowest-probability disjunctive clause.

Because thousands of conditions are combined and compared during segmentation, keeping boolean expressions normalized is critical. We represent every ActivationCondition in monotonic Conjunctive Normal Form (CNF) and simplify via clause subsumption: if clause A is a subset of clause B, B is redundant and dropped. When computing Or(A, B), we avoid exponential blowup by factoring out identical clauses shared between A and B in a single linear pass before taking the cross product of the remaining clauses.

Part 3: Cost-Based Merging & Multi-Script Optimization

Minimizing expected bytes transferred across languages

Once we have our initial fine-grained patches and their normalized CNF conditions, we enter Part 3: the cost-based merger.

Why Merge Segments & Patches?

Starting with one segment per codepoint yields hundreds or thousands of tiny glyph patches.

Merging combines segments or patches to balance two competing forces:

  • Per-Patch Overhead (k) vs.
  • Unneeded Glyph Transfer ("Over-fetching")

Benefits of Careful Merging

  • Reduces HTTP Request Overhead: Fewer patch fetches per page view.
  • Improves Brotli Compression: Glyphs within a script share contour patterns and deltas; compressing them together in one patch yields much higher compression ratios.
  • Shrinks Patch Map Tables: Fewer conditions and entries in the initial font's IFT / IFTX tables.

Risk of Bad Merging

  • Merging a rare character into a high-frequency character forces clients to download the rare glyph on almost every page view!

Why do we need a cost-based merger? If we leave one segment per codepoint, the client pays a per-request network overhead on every patch and loses cross-glyph Brotli compression dictionary synergy. On the other hand, if we merge a rare character with a common character like 'e', every user downloads the rare glyph unnecessarily. We need a quantitative objective function to evaluate every candidate merge.

The Segmentation Cost Function

We quantify the performance of a candidate glyph segmentation S = {p1, …, pn} by the expected number of bytes transferred for a random page view (docs/segmenter.md):

cost(S)  =  size(Finit)  +  ∑i=1..n P(ci) × (size(pi) + k)

P(ci) ∈ [0, 1]

Probability that patch pi's activation condition ci is satisfied on a random web page (estimated from codepoint unigram or bigram frequencies).

size(pi) (bytes)

Size of glyph-keyed patch pi after Brotli compression. Using real Brotli compression captures cross-glyph outline redundancy!

k (bytes)

Fixed network & format overhead per patch request (configurable via network_overhead_cost; default 200 bytes in auto-config).

Our cost function is simple and physically grounded: the expected number of bytes transferred per page view. Each patch pi contributes its activation probability P(ci) multiplied by its Brotli-compressed byte size plus a fixed per-request network overhead k (set to 200 bytes based on measurements from the IFT demo). Crucially, computing size(pi) with actual Brotli compression lets the merger discover pairs of glyphs whose outlines compress well together.

Assessing Candidate Merges via Cost Deltas (Δcost)

Because each patch contributes independently to cost(S), evaluating a candidate merge only requires inspecting the localized subset of patches affected by the merge (candidate_merge.cc):

Δcost  =  ∑p ∈ Added ∪ Modified P(c′p) · (size(p′) + k)  −  ∑p ∈ Removed ∪ Modified P(cp) · (size(p) + k)

Effects of a Candidate Merge

  1. Remove or add patches: e.g., two exclusive patches merge into one combined patch.
  2. Modify glyphs in existing patches: e.g., interaction glyphs move from a conditional patch into the merged exclusive patch.
  3. Modify activation conditions: e.g., replacing merged segment IDs in downstream CNF clauses.

Greedy Merge Loop

  • Use the inverted index (TriggeringSegmentToConditions) to locate all patches whose conditions reference the candidate segments.
  • Compute Δcost for candidate pairs in the Merge Group.
  • Select the pair with the lowest (most negative) Δcost < 0, apply the merge, and repeat until no negative-cost merges remain.

Because the total cost is a sum over independent patches, we never recompute the cost of the entire font to test a candidate merge. Instead, we use an inverted index from triggering segments to conditions to find only the patches touched by the merge, subtract their old cost contribution, and add back the new cost contribution. That difference is the cost delta (Δcost). Any merge with Δcost < 0 reduces expected network transfer.

Segment Merging vs. Patch Merging

The merger supports two distinct merge operations with different closure behaviors:

1. Segment Merge (sa ∪ sb → sab)

Unions the codepoints/features of two input segments and updates glyph conditions across the dependency graph:

  • Example ({f}, {i}, and ligature {fi}):
    Merging segments {f} and {i} into {f, i} collapses all three patches ({f}, {i}, and {fi}) into a single exclusive patch {f, i, fi}!
  • Ideal for merging exclusive patches and resolving conjunctive ligature/composite patches into their parent segments.

2. Patch Merge (p1 ∪ p2 → p12)

Directly combines two specific glyph patches without modifying input segment definitions (experimental_use_patch_merges):

  • New patch has glyphs Glyphs(p1) ∪ Glyphs(p2) and condition Or(c1, c2).
  • Example: Merging patch {f} and patch {i} via a Patch Merge creates {f, i} with condition (f OR i), while leaving the {fi} patch (f AND i) untouched!
  • Ideal for combining non-exclusive (conjunctive/disjunctive) patches where a full Segment Merge would pull in too many unrelated closure glyphs.

We distinguish between two types of merges: a Segment Merge and a Patch Merge. A Segment Merge unions the underlying Unicode segments sa and sb, which automatically folds any conjunctive interaction glyphs like fi into the merged patch. A Patch Merge, on the other hand, leaves the input segments alone and directly unions two specific glyph patches while OR-ing their activation conditions. Patch merges are particularly effective for non-exclusive patches where merging the underlying segments would pull in too many unrelated glyphs via closure.

Initial Font Merging & Fallback Glyphs

Before general pairwise merging, Merger::MoveSegmentsToInitFont checks which high-frequency segments belong in the Initial Font (s0):

Why Move Glyphs to s0?

  • For glyphs needed with near-100% probability (e.g., core Latin lowercase letters in an English font), loading them conditionally in a patch wastes network overhead k, patch headers, and a client round trip.
  • Moving a segment si into s0 also simplifies downstream conditions (conjunctive edges depending on si become disjunctive or exclusive!).

Initial Font Δcost & Thresholds

  • Prunes segments below initial_font_merge_probability_threshold (25%–60% depending on Quality Level).
  • Computes Δcostinit, adding the WOFF2 size increase Δsize(Finit) and subtracting eliminated patch costs.
  • Accepts the move if Δcostinit < threshold (default −0.8 × k = −160 bytes).
  • Unmapped / Fallback Glyphs: Any glyphs whose conditions cannot be isolated are moved into s0 by default (MOVE_TO_INIT_FONT).

Before running pairwise patch merging, we run Initial Font Merging. If a character occurs on nearly 100% of web pages in the primary script, keeping it in a separate patch just adds header and request overhead. We evaluate segments above the probability threshold by measuring how much the initial WOFF2 font grows versus how much expected patch transfer cost is eliminated. If the net cost savings exceeds 80% of a network request (-160 bytes), we move the segment directly into the initial font.

Estimating Activation Condition Probabilities

To evaluate cost(S), ProbabilityCalculator estimates P(ci) from web corpus frequency data in w3c/ift-encoder-data (stored as sorted Riegeli records of CodepointCount):

1. Frequency Unigrams (use_bigrams = false)

Quality 1–2 Uses only single-codepoint probabilities P(a), assuming all codepoints occur independently:

  • Disjunction: P(a1 ∨ … ∨ ak) = 1 − ∏i=1..k (1 − P(ai))
  • Conjunction: P(S1 ∧ … ∧ Sm) = ∏j=1..m P(Sj)
  • Pros: Very fast O(k) evaluation; tiny 1.5 MB dataset.
  • Cons: Independence is false on real text—characters in a script co-occur, so unigrams systematically overestimate union probabilities P(a ∪ b).

2. Frequency Bigrams (use_bigrams = true)

Quality 3–7 Uses empirical pairwise co-occurrence probabilities P(a ∩ b) (probability a page contains both a and b):

  • No Independence Assumption: Captures real-world character correlation (e.g., q and u, or common Kanji pairs).
  • Because we have 1st- and 2nd-order marginals (P(a) and P(a ∩ b)) but not k-way joint distributions, exact probabilities for k ≥ 3 are underdetermined.
  • Instead, we compute rigorous Probability Bounds [Pmin, Pmax]!

How do we compute P(ci) for a boolean condition over codepoints? We have two modes. Unigram mode uses only individual codepoint probabilities and assumes statistical independence—which is fast, but overestimates the probability of unions because characters on web pages are correlated. Bigram mode, used in Quality 3 through 7, uses pairwise co-occurrence counts P(a ∩ b) from our 696 MB Riegeli dataset to compute rigorous upper and lower probability bounds without assuming independence.

Bigram Probability Bounds: Unions & Intersections

Given S1 = ∑i=1..n P(ai) and S2 = ∑1≤i<j≤n P(ai ∩ aj) for a disjunctive clause U = ⋃i=1..n ai:

1. Disjunctive Clauses: Dawson–Sankoff / Kwerel (1975) Bounds

From "Bounds for the Probability of a Union, with Applications" (Formulas 3 & 4), let k* = ⌊2S2 / S1⌋ + 1:

  • Lower Bound (Pmin, optimal degree-2 bound): P(U)  ≥  [ 2 / (k* + 1) ] · S1 − [ 2 / (k*(k* + 1)) ] · S2
  • Upper Bound (Pmax, Hunter–Worsley / Kwerel bound): P(U)  ≤  min( 1.0,  S1 − (2 / n) · S2 )

2. Conjunctive Clauses across Segments & Point Selection

  • For conjunctions C1 ∧ … ∧ Cm across clauses, we apply the Fréchet inequalities: max( 0,  ∑j=1..m Pmin(Cj) − (m − 1) )  ≤  P( ∩j=1..m Cj )  ≤  min1≤j≤m Pmax(Cj)
  • Cost Evaluation Value: Uses the midpoint P(ci) = ½ (Pmin(ci) + Pmax(ci)).

Specifically, for a union of codepoints a1 ∪ … ∪ an, we compute the sum of single probabilities S1 and the sum of pairwise probabilities S2, and plug them into Formulas 3 and 4 from Kwerel (1975) / Dawson–Sankoff, which give the provably tightest possible lower and upper bounds using degree-2 marginals. For conjunctions across clauses, we use the classic Fréchet bounds, and then take the midpoint of [Pmin, Pmax] when evaluating the cost function.

Multi-Script Fonts & Merge Group Isolation

When a font supports multiple writing scripts or languages, two fundamental challenges arise (docs/segmenter.md):

The Multi-Script Challenges

  1. Missing Cross-Script Bigrams: Frequency data is collected per script/language; we don't have bigram pair counts between e.g. 1 Latin and 1 Cyrillic codepoint.
  2. Conflicting Frequencies on Shared Codepoints: Under Han unification, Simplified Chinese, Traditional Chinese, Japanese, and Korean share thousands of CJK ideographs that occur with vastly different frequencies in each language.

Design Principle & Isolation

  • Equal Importance Principle: We do not normalize by global web language prevalence (which would optimize for high-traffic languages at the expense of minority scripts).
  • Merge Group Isolation: Disjoint scripts are partitioned into isolated MergeGroups:
    • Avoids cross-script merges where pair probabilities are unknown.
    • Bounds the quadratic O(n2) candidate search space to within each individual merge group!

When encoding a multi-script font, we face two challenges: missing cross-script bigram probabilities for disjoint scripts like Latin and Cyrillic, and conflicting probabilities for overlapping scripts like CJK. A key design principle of our encoder is that every supported script is treated with equal importance rather than weighting by global internet traffic. We isolate disjoint scripts into separate Merge Groups, which both prevents cross-script merges and shrinks the quadratic O(n2) search space.

Multi-Dataset Cost Function & Pagg Optimization

Within a single Merge Group configured with M frequency datasets (e.g., M = 4 for CJK), the total cost is the unweighted sum across all M datasets:

cost(S)  =  ∑m=1..M costm(S)  =  ∑m=1..M ∑pi ∈ S Pm(ci) × (size(pi) + k)

Cost Delta Optimization: Factoring Out Patch Size

When evaluating a candidate merge across M datasets, the compressed patch size size(pi) and network overhead k are identical across all M datasets—only Pm(ci) varies! By linearity:

∑m=1..M Pm(ci) × (size(pi) + k)  =  (size(pi) + k) × [ ∑m=1..M Pm(ci) ]Pagg(ci)

Computing the aggregate probability Pagg(ci) = ∑m=1..M Pm(ci) first and multiplying once by (size(pi) + k) eliminates M× redundant patch size lookups and inner delta loops!

Inside a multi-script merge group like CJK—which has four frequency datasets—we define the group cost as the unweighted sum of the costs across all M datasets. Naively, evaluating every candidate merge against M datasets would multiply our inner loop work by M. However, notice that a patch's compressed size size(pi) and network overhead k do not depend on the language dataset! By factoring (size(pi) + k) out of the sum, we simply sum the condition probabilities across the M calculators to get Pagg(ci) and multiply by the patch size once.

Prioritizing a Primary Script & Group Splitting

When a font is deployed for a specific primary locale (e.g., --auto_config_primary_script=Script_japanese), the segmenter biases optimization in two ways:

1. Scoped Initial Font Merging

  • Infrequently used secondary scripts should never force their high-frequency characters into the Initial Font (s0).
  • initial_font_merge_threshold is configured per FrequencyDataConfig profile.
  • Only the primary script's profile opts into Initial Font Merging, evaluated solely against the primary script's probabilities.

2. Overlapping Cluster Splitting

  • If Japanese were left in the unified 4-way CJK merge group, Han ideographs used in Japanese would be weighted equally across Chinese, Japanese, and Korean.
  • Instead, AutoSegmenterConfig splits the cluster into two disjoint merge groups:
    1. Primary Group (Japanese): Covers all font codepoints in Script_japanese, optimized 100% for Japanese.
    2. Secondary Group (Hans+Hant+Korean): Restricted to remaining CJK codepoints not in Japanese, optimized equally across the remaining 3 scripts.

What if a user explicitly specifies a primary script, like Script_japanese on a full CJK font? First, only the Japanese profile is allowed to move glyphs into the initial font. Second, instead of leaving Japanese in a single 4-way CJK merge group, AutoSegmenterConfig splits the CJK cluster into two disjoint groups: a primary group for all codepoints covered by Japanese (optimized 100% for Japanese frequencies), and a secondary group for the remaining CJK codepoints not used in Japanese (optimized with equal weight across Simplified Chinese, Traditional Chinese, and Korean).

Minimum Group Sizes & Heuristic Fallback

Minimum Group Size (Privacy)

The W3C IFT specification recommends a minimum number of codepoints per patch activation condition (min_group_size = 4) to prevent single-character text fingerprinting:

  • A condition's effective group size is the size of its smallest disjunctive clause: EffectiveGroupSize(C)  =  minCk ∈ C |Ck|
  • Phase A (Cost Reduction): Merger only accepts candidate merges with Δcost < 0.
  • Phase B (Group Size Enforcement): For any remaining patches with EffectiveGroupSize < min_group_size, the merger accepts positive Δcost merges, greedily picking the least positive Δcost until all conditions meet the minimum group size!

Heuristic Merging (Uncovered Codepoints)

Fonts often contain symbols, PUA glyphs, or rare scripts not covered by frequency data (ungrouped_config):

  • Without probability data, we use HeuristicConfiguration (min_patch_size = 2500 bytes, max_patch_size).
  • Pre-groups ungrouped segments in blocks of 3 × min_group_size = 12.
  • For any patch below min_patch_size, merges adjacent exclusive patches (or segments in composite conditions) in codepoint order as long as the combined size stays ≤ max_patch_size.

To protect user privacy and prevent single-character fingerprinting, the IFT spec recommends a minimum group size (4 codepoints by default). Our cost merger handles this in two phases: first, it performs all merges that have a negative Δcost. Second, if any patches still have an effective group size below 4, it allows positive Δcost merges for those undersized patches, always choosing the candidate with the smallest cost penalty. For codepoints not covered by frequency datasets, a fast heuristic merger groups adjacent segments until patches reach at least 2,500 bytes.

Part 4: Key Optimization Techniques & Validation

Pruning O(n2) Brotli evaluations, inert segments, caching & closure verification

Now let's examine Part 4: the algorithmic optimizations that make cost-based segmentation fast in practice, followed by how we validate the final segmentation plan.

The Bottleneck: O(n2) Brotli Compressions

Why is naive cost-based merging slow on large fonts?

  • A CJK font can start with n > 20,000 individual codepoint segments.
  • Evaluating all pairwise candidate merges requires C(n, 2) = O(n2) cost delta evaluations—and each evaluation needs the Brotli-compressed size of the combined glyph patch!
  • Profiling shows that Brotli compression accounts for the vast majority of segmenter runtime, followed by condition/closure updates after non-trivial merges.

Five Pillars of Merger Optimization

  1. Best-Case Probability & Size Pruning: Reject candidates mathematically before calling Brotli.
  2. Pre-Closure Grouping & Low-Impact Cutoff: Shrink n upfront and skip O(n2) search on the zero-probability long tail.
  3. Inert Segment Exploitation: Fast-path segments that have no cross-segment glyph dependencies and batch initial-font merges.
  4. Multi-Layer Caching & Brotli Quality Tiers: Memoize patch sizes, closures, and probabilities; tune Brotli quality (0, 9, 11).
  5. Incremental Dependency Graph Updates & Base-Segment Composite Filtering: Reprocess only the affected subgraph on each merge.

If we naively implemented the greedy merger on a 20,000-codepoint font, evaluating C(n, 2) pairs would require hundreds of millions of Brotli compressions. Profiling confirms that Brotli compression dominates runtime. To make the segmenter practical across the entire Google Fonts corpus, we rely on five key optimization techniques.

Optimization 1: Best-Case Cost Pruning

Before running Brotli to measure size(A ∪ B), we compute a lower bound on the merged patch size using the already-known sizes of patches A and B (candidate_merge.cc):

sizebest(A ∪ B)  =  max(size(A), size(B))  +  fbest × min(size(A), size(B))  +  header_overhead

Theoretical vs. Empirical Bound (fbest)

  • Theoretical lower bound (fbest = 0): The smaller patch's outline data is 100% redundant with the larger patch and compresses to 0 extra bytes.
  • Empirical bound (best_case_size_reduction_fraction = 0.5): Across real fonts at Brotli Q9, only 0.2% of glyph pairs compress to less than 0.5 × min(size(A), size(B)).

Early Rejection Without Brotli

  1. Compute P(cA∪B) and plug sizebest(A ∪ B) into the Δcost formula.
  2. If Δcostbest ≥ 0 (or Δcostbest ≥ Δcostcurrent_best):
    Prune the candidate pair immediately!
  3. Eliminates the vast majority of Brotli compression calls with negligible impact on final segmentation cost.

Our most impactful pruning technique is Best-Case Cost Pruning. Before we ever invoke Brotli on a candidate merge of patches A and B, we ask: what is the smallest possible byte size the combined patch could have? Theoretically, it's max(size(A), size(B)) if the smaller patch compresses for free. Empirically, across real fonts at Brotli 9, 99.8% of pairs retain at least 50% of the smaller patch's compressed size (best_case_size_reduction_fraction = 0.5). If even that best-case size cannot beat our current best Δcost (or cannot produce a negative Δcost), we skip the Brotli compression entirely.

Optimization 2: Low-Impact Cutoff & Pre-Grouping

Codepoint frequencies follow a steep Zipfian distribution: a long tail of rare characters has P(ci) ≈ 0 and contributes almost nothing to cost(S) = ∑ P(ci)(size(pi) + k).

1. Pre-Closure Grouping (PreGroupSegments)

  • Sorts segments within each merge group by descending probability P(si).
  • Before running condition analysis or closure, adjacent non-feature segments with P(si) ≤ threshold (0.05% to 5% by Quality Level) are pre-merged into groups of kMinimumGroupSize = 4.
  • Impact: Immediately reduces n by up to 4× before any O(n2) work begins!

2. Optimization Cutoff (optimization_cutoff_fraction)

  • Computes each segment's baseline cost contribution P(si) · (size(pi) + k).
  • Segments in the bottom tail whose cumulative contribution is below optimization_cutoff_fraction (0.5% to 5%) have cost optimization disabled.
  • Excluded from O(n2) best-pair search; when merged to meet min_group_size, they simply merge with the next available segment in O(1) steps!

Second, we exploit the heavy-tailed Zipfian distribution of character frequencies. Most scripts have a long tail of rare codepoints whose probabilities are near zero. First, during PreGroupSegments, segments below the preprocess probability threshold are grouped into chunks of 4 before we even build the dependency graph. Second, segments in the bottom 0.5% to 5% of total cost contribution are marked as cutoff segments: we skip O(n2) pair evaluation on them completely, dramatically shrinking the effective n in O(n2).

Optimization 3: Inert Segments & Incremental Updates

Exploiting Inert Segments

An inert segment is a segment whose codepoints only activate exclusive glyphs and never interact with any other segment in GSUB, cmap 14, or glyf:

  • Closed Under Union: Merging two inert segments is guaranteed to produce a new inert segment whose glyph set is simply Ga ∪ Gb—zero dependency graph or closure re-evaluation needed!
  • Batch Initial Font Merging: Because inert segments don't interact with each other, merging one into s0 barely affects the Δcost of another. We evaluate all inert candidates in a single pass and apply them as a batch!

Incremental Graph Updates & Filtering

  • Partial Invalidation (ReprocessChanged): When non-inert segments merge into sbase, DependencyClosure::SegmentsToAffectedGlyphs locates only the glyphs reachable from sbase and recomputes conditions exclusively for that subgraph.
  • Base-Segment Composite Filtering: When evaluating 3+-way composite condition merges, restricting candidates to composite conditions that already reference base_segment_index cuts total Google Fonts corpus segmentation time by ~15% (and up to 86% on complex Arabic fonts like Amiri).

Third, we identify "inert segments" during condition analysis—segments that only map to exclusive glyphs and have zero multi-segment interactions. When two inert segments merge, the resulting segment is guaranteed to be inert and its glyph set is simply the union of the two glyph sets, requiring zero condition recomputation. Even better, during initial font merging, we can evaluate all inert segments in one pass and move them into the initial font in a single batch. And when non-inert segments merge, we use the dependency graph to incrementally update only the affected glyphs.

Optimization 4: Multi-Layer Caching & Brotli Tiers

1. PatchSizeCache

Maps GlyphSet → uint32_t (compressed bytes):

  • Memoizes exact Brotli-compressed `.ift_gk` patch sizes.
  • Prevents ever re-compressing the same glyph set across merge iterations.
  • Tracks hit/miss statistics.

2. GlyphClosureCache

Maps SubsetDefinition → GlyphSet:

  • Preprocesses hb_face_t once via hb_subset_preprocess.
  • Expands UnicodeClosure and caches HarfBuzz subsetter plans.

3. Probability Caches

Inside each ProbabilityCalculator:

  • Caches single-segment bounds P(si) in a dense vector.
  • Caches disjunctive clause bounds P(si1 ∨ … ∨ sik) in a hash map keyed by SegmentSet.

Configurable Brotli Quality Tiers (brotli_quality & EstimatedPatchSizeCache)

  • Brotli Quality 11 (Q6–Q7): Maximum compression accuracy; used for final encoding and small fonts.
  • Brotli Quality 9 (Q4–Q5): Orders of magnitude faster than Q11 with nearly identical merge decisions.
  • Brotli Quality 0 (Q1–Q3, EstimatedPatchSizeCache): Computes the input font's overall outline compression ratio once at startup and estimates size(p) = raw_outline_bytes(p) × ratio in O(1) time without calling Brotli!

Fourth, we layerthree caches across the segmenter: PatchSizeCache memoizes compressed patch sizes by GlyphSet; GlyphClosureCache memoizes HarfBuzz closure results on a pre-processed face; and each ProbabilityCalculator caches both single-segment and disjunctive subgroup probability bounds. On top of caching, we allow tuning the Brotli quality used during merge evaluation—from Quality 11 down to Quality 9, or Quality 0 where EstimatedPatchSizeCache estimates patch sizes from raw glyph byte counts using the font's baseline compression ratio.

Closure Requirement Validation

Before emitting the final SegmentationPlan, the segmenter runs two verification passes (segmentation_context.cc):

1. ValidateIncrementalGroupings

  • Creates a fresh SegmentationContext with the final merged segments and combined patch partitions.
  • Re-runs condition analysis and grouping from scratch (non-incrementally).
  • Verifies that the incrementally maintained conditions and glyph groupings match the clean full recomputation.

2. ValidateSegmentation (Closure Check)

  • Partition Check: Verifies s0 and all patch glyph sets Gp are strictly disjoint and their union equals FullClosure().
  • No Missing Conditions Check (HasAdditionalConditions):
    For every patch Gp and every disjunctive clause Ck = (sk,1 ∨ … ∨ sk,m) in its CNF condition, computes the HarfBuzz glyph closure of all segments except Ck: closure(F,  Sall ∖ Ck)  ∩  Gp  =  ∅ Proves no glyph in Gp can ever be needed when Ck is false!

How do we guarantee that our dependency graph and incremental merger never violate the HarfBuzz closure requirement? At the end of segmentation, we run two strict validation checks. First, ValidateIncrementalGroupings recomputes all glyph conditions from scratch and asserts equivalence with the incremental state. Second, ValidateSegmentation verifies that every glyph in FullClosure() is placed in at most one patch, and then for every disjunctive clause Ck of every patch's condition, it runs actual HarfBuzz closure on the complement set Sall ∖ Ck to prove that none of the patch's glyphs can be reached without Ck!

Part 5: The IFT Compiler

Table-keyed patch graphs, recursive compilation & OpenType table handling

Finally, let's dive into Part 5: the IFT Compiler (ift/encoder/compiler.cc), which takes the SegmentationPlan and compiles the actual WOFF2 initial font and patch files.

Compiler Overview & The Table-Keyed Patch Graph

While Glyph-Keyed patches (.ift_gk) are independent per-glyph outline bundles, Table-Keyed patches (.ift_tk) are invalidating binary diffs over non-outline tables (cmap, GSUB, GPOS, etc.) that form a Directed Acyclic Graph (DAG):

  • Nodes: Uniquely identified by the SubsetDefinition (codepoints, features, design space) covered at that state.
  • Edges & Jumps: An edge transitions from base node A to target node A ∪ Δ via one or more sequential patch applications (jumps).

In the compiler, table-keyed patches form a Directed Acyclic Graph. Every node in the DAG represents an extended state of the font's non-outline tables (e.g., initial font A, A+B, A+C, A+B+C), and every edge represents extending the font with one or more non-outline segments (typically one segment per script plus one for optional layout features).

Table-Keyed Patch Graph Shape Parameters

With S table-keyed segments, a full hypercube has ∑d=0..S−1 C(S, d)(S − d) = S · 2S−1 single-step patches! Four parameters in SegmentationPlan control the tradeoff between client round trips and total patch count:

1. jump_ahead (Auto-Config: 2)

Adds outgoing edges at each node for all combinations of 2 … jump_ahead segments simultaneously, allowing multi-segment extensions in a single round trip.

2. use_prefetch_lists (Auto-Config: true)

Instead of emitting a new binary patch for a multi-segment edge like A → A+B+C, encodes the edge as a Prefetch List of existing single-segment patches:
[patch(A → A+B), patch(A+B → A+B+C)].
Client fetches both in 1 round trip and applies them sequentially—eliminating combinatorial patch explosion!

3. max_depth (Auto-Capped ≤ 2048 patches)

Caps the maximum depth (round trips) of the DAG. At depth max_depth − 1, each node has a single outgoing patch that adds all remaining segments at once:

Patches(S, D)  =  ∑d=0..D−2 C(S, d) · (S − d)  +  C(S, D − 1)

ConfigureMaxDepth reduces max_depth (down to floor 3) whenever estimated patches exceed 2048.

4. include_all_segment_patches

Optional flag that adds a direct "add all remaining segments" patch at every node in the graph.

If a font has many scripts, a full hypercube of table-keyed patches grows as S · 2S−1. We shape this graph with four parameters in SegmentationPlan: jump_ahead = 2 lets clients add two script segments in a single round trip; use_prefetch_lists = true encodes multi-segment edges by listing a sequence of single-segment patches in the IFT Format 2 prefetch list rather than creating new patch binaries; and max_depth caps the depth of the graph so that total table-keyed patches stay under 2,048.

Recursive Compilation Algorithm (Compile)

Starting at the Initial Font subset definition, Compiler::Compile recursively traverses the table-keyed graph (compiler.cc):

  1. Generate Glyph-Keyed Patch Set (Cached by Design Space):
    For the node's variable design space, instance the original font to that design space and extract per-glyph outline slices (glyf/gvar/CFF/CFF2) for each patch in glyph_patches. Compress with Brotli (.ift_gk) and assign a 128-bit Patch Set Compatibility ID.
  2. Assign Node Compatibility ID & Enumerate Outgoing Edges:
    Generate a unique 128-bit Compatibility ID for the current node and construct all single-segment, jump_ahead, use_prefetch_lists, and max_depth outgoing edges.
  3. Optimize & Serialize Patch Map Tables (EntryGraph):
    Convert CNF glyph activation conditions and table-keyed edges into Format 2 Patch Map entries (IFT and IFTX), running EntryGraph::Optimize() to share common sub-entries and minimize table byte size.
  4. Construct & Cache Node Font Binary:
    Subset the original font to the node's base subset definition, attach the IFT /IFTX mapping tables, and cache the resulting font binary.
  5. Recurse on Outgoing Jumps & Emit .ift_tk Diffs:
    For each jump B → B′, recursively compile B′ and run per-table Brotli shared-dictionary diffing between B and B′ (cached by patch ID).

Here is the 5-step recursive algorithm in Compiler::Compile. At each node, we first generate (or look up in cache) the glyph-keyed patch set for the node's variable design space. Next, we enumerate outgoing table-keyed edges and compile both glyph-keyed and table-keyed conditions into Format 2 Patch Map tables using EntryGraph::Optimize() to deduplicate shared sub-clauses. Then we subset the font to the current node, insert the IFT and IFTX tables, and recursively compile target nodes to generate the Brotli shared-dictionary table-keyed patches.

Compiler: OpenType Special Handling & Testing

OpenType Table Special Casing

  • Retain GIDs & Max GID: Subsets with HB_SUBSET_FLAGS_RETAIN_GIDS and retains the highest GID so maxp.numGlyphs accommodates all reachable .ift_gk patches.
  • Long loca Offsets: Forces 32-bit loca offsets from the start if the fully extended glyf table needs them (since .ift_gk patches cannot alter head.indexToLocFormat).
  • Two-Step gvar Subsetting: (1) Instance design space only; (2) subset glyphs without instancing—preserving identical gvar header shared tuples across nodes and .ift_gk patches.
  • CFF / CFF2 Desubroutinization: Desubroutinizes charstrings upfront so per-glyph outlines are self-contained, and rebuilds CharStrings at the end of the table.
  • WOFF2 Round-Trip: Round-trips the initial font through WOFF2 (with glyf/loca transforms disabled) so .ift_tk diffs match the client's decoded bytes.

End-to-End Integration Testing

Verified in ift/integration_test.cc by encoding real fonts (TrueType, CFF, CFF2, Variable, Multi-Script) and extending them with the Fontations IFT Client (incremental-font-transfer):

  • Closure & Outline Equality: Asserts cmap coverage and per-glyph outline presence/bytes match the original font after extension.
  • Network Efficiency: Verifies exact client round-trip counts (e.g. 1 RT with jump_ahead / prefetch lists) and total patch loads.
  • Future Compiler Work:
    • Glyph-keyed-only encoding mode
    • Sorting table-keyed patch map entries by patch byte size
    • Conjunctive matching on multi-segment table-keyed entries

Making table-keyed subsetting and glyph-keyed outline patching work seamlessly together requires careful OpenType engineering: retaining GIDs, forcing long loca offsets when needed, two-step gvar subsetting so shared tuples stay synchronized with glyph patches, desubroutinizing CFF/CFF2 charstrings, and round-tripping the initial font through WOFF2 before diffing. All of this is continuously verified in integration tests against the Rust Fontations IFT client.
