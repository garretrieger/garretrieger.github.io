Incremental Font Transfer (IFT) Encoder Deep Dive

Google Fonts · W3C WebFonts WG
TPAC 2026

Welcome everyone. Today we're doing a technical deep dive into the W3C Incremental Font Transfer (IFT) reference encoder (w3c/ift-encoder)—covering how we go from an arbitrary OpenType font to an optimized set of glyph-keyed and table-keyed patches that preserve shaping closure while minimizing expected bytes transferred.

Agenda

  1. Pipeline & Workflows: Auto config, segmenter, compiler
  2. Automatic Configuration: Script clustering, quality levels (1–7)
  3. Dependency Graph & Conditions: Closure, Tarjan SCC, CNF
  4. Cost-Based Merging: Expected bytes, bigram bounds, multi-script Pagg
  5. Key Optimizations: Best-case pruning, cutoffs, inert segments, caching
  6. The IFT Compiler: Table-keyed patch DAG, prefetch lists, OpenType rules

Here is our roadmap. We'll start with the three-stage encoding pipeline and CLI workflows, then cover automatic configuration, the Unicode and glyph dependency graph, condition extraction, cost-based merging, our core performance optimizations, and finally the IFT compiler.

IFT Encoding Model

Compact Initial Font (WOFF2) with patch maps (IFT / IFTX).

  • Outlines: glyf, loca, gvar, CFF, CFF2
  • Non-Outlines: cmap, GSUB, GPOS, COLR, ...

Two Patch Types

  • Glyph-Keyed (.ift_gk): Additive per-glyph data
  • Table-Keyed (.ift_tk): Brotli binary diffs per table.
  • Mixed Mode: Coarse .ift_tk + fine .ift_gk.

An IFT encoding splits font data into outline tables and non-outline tables. Outline tables are extended via Glyph-Keyed patches, which are additive per-glyph bundles. Non-outline tables are extended via Table-Keyed patches, which are binary diffs relative to a specific base font state. The encoder operates in Mixed Mode by default.

Three-Stage Encoding Pipeline

  • Stages 1 & 2 optimize the plan; Stage 3 deterministically compiles it.
  • Inspectable segmenter_config.proto and segmentation_plan.proto.

Under the hood, IFT font encoding happens in three distinct stages separated by protobuf schemas. Stage 1 analyzes the font and builds a SegmenterConfig. Stage 2 runs the dependency graph analyzer and cost-based merger to produce a SegmentationPlan. Stage 3 compiles the plan and original font into the final WOFF2 initial font and patch files.

Single-Step Workflow: font2ift

font2ift --input_font=MyFont.ttf \
  --output_path=ift/ --output_font=MyFont.woff2

Primary Script

  • --auto_config_primary_script
  • Target script or language (e.g., Script_japanese).
  • Merges top glyphs into initial font & priotizes script when there are overlaps.

Quality Level

  • --auto_config_quality (1 to 7)
  • Trades CPU time for smaller transfer bytes.
  • Auto-selected by heuristic if omitted.

For most users, font2ift provides a single-command workflow. You give it an input font and output path, and it automatically generates a config, segments the font, and compiles the output. Two optional flags let you guide auto-configuration: --auto_config_primary_script and --auto_config_quality. Setting a primary script tells the segmenter to prioritize that script when generating the plan: first the primary script is eligible to have it's codepoints moved into the init font if they are high probability, second when there other other scripts overlapping the primary script, then the primary script takes precedence. It's cost is optimized first ahead of the non-primary scripts.

Multi-Step Advanced Workflow

  1. Generate Config: 
    gen_ift_segmenter_config --quality=5 \
  --input_font=MyFont.ttf > config.txtpb
  2. Generate Segmentation Plan: 
    gen_ift_segmentation_plan --config=config.txtpb \
  --input_font=MyFont.ttf > plan.txtpb
  3. Compile Font & Patches: 
    font2ift --input_font=MyFont.ttf --plan=plan.txtpb \
  --output_path=out/ --output_font=MyFont.woff2

For advanced use cases—such as inspecting intermediate plans, supplying custom frequency datasets, or tuning merge parameters—each stage has its own CLI utility: gen_ift_segmenter_config, gen_ift_segmentation_plan (or gen_ift_table_keyed_plan), and finally font2ift --plan=....

Part 1: Automatic Configuration

Script detection, overlap clustering, quality levels & heuristics

Let's now dive into Part 1: how AutoSegmenterConfig analyzes an input font and constructs an effective segmentation configuration automatically.

What AutoSegmenterConfig Does

  1. Script Detection: Matches codepoints against 183 datasets in ift-encoder-data.
  2. Overlap Clustering: Unions scripts with ≥ 10% overlap into shared MergeGroups.
  3. Primary Script Priority: Scopes initial-font merging and splits clusters.
  4. Table-Keyed Setup: 1 segment/script, jump_ahead=2, prefetch lists, max_depth.
  5. Quality Selection: Applies level 1..7 or the Auto Quality Heuristic.

AutoSegmenterConfig::GenerateConfig is responsible for five key tasks: detecting which scripts are present in the font, clustering overlapping scripts into merge groups, prioritizing the primary script, bounding the table-keyed patch graph size, and configuring quality/runtime tradeoffs.

Segments & Merge Groups

Segment

  • Grouping of codepoints + layout features.
  • Smallest unit the font can be extended by.

Merge Group

  • Partitions input segments.
  • No cross group merges allowed.

Why Isolate Groups?

  • Script Separation: Keeps disjoint scripts (e.g. Latin, Cyrillic) separate.
  • Bounds O(n2) Search: Limits quadratic pair evaluation to each group.

Before looking at how scripts are detected and clustered, let's define two core concepts: a Segment is a grouping of Unicode codepoints and layout features that acts as the smallest unit the font can be extended by. A Merge Group partitions input segments into isolated subsets, where each group is optimized independently using its own frequency datasets. Isolating merge groups prevents cross-group merges, keeps disjoint scripts like Latin and Cyrillic separate, and bounds the quadratic O(n2) candidate search to each individual group.

Script Detection & Overlap Clustering

1. Script Detection

  • Look for > 1 unique codepoints (not in other scripts)
  • CJK special cased due to high overlap.

2. Overlap Clustering

  • Divides scripts into merge groups.
  • Ignores spaces, controls & combining marks.
  • Scripts with ≥ 10% shared probability mass are placed in the same group.

If two scripts share codepoints and are placed in separate merge groups, those shared codepoints are excluded from cost merging. Conversely, grouping on any shared codepoint chains everything together via spaces and punctuation. We filter out spaces, controls, and combining marks, and union scripts whose shared codepoints cover at least 10% of either script's unigram probability mass (kScriptOverlapThreshold = 0.10).

The Auto Quality Heuristic

Selection Criteria

  • f(number of codepoints) -> quality level
  • Goal: 99.5% of fonts take < 15 minutes.

Limits & Future Work

  • Limits: doesn't account for high GSUB complexity.
  • Time Budget: estimate brotli and dep graph cost for a font.

When the user omits a quality flag, AutoPickQuality picks a default quality level as a function of the number of codepoints in the font, calibrated across the Google Fonts library so that fewer than 0.5% of fonts take longer than 15 minutes to segment. In the future, we plan to evolve this into a time-budget estimator that samples Brotli/closure speed and factors in per-merge-group sizes and condition complexity.

Part 2: Glyph Segmentation & Dependency Graph

Mapping Unicode codepoints & features to closure-safe glyph patches

Now let's move to Part 2: how the segmenter bridges the gap between Unicode codepoints in the client's text and Glyph IDs in the font's outline tables.

The Glyph Segmentation Problem

Codepoints vs. Glyphs

  • Conditions match codepoints & features; patches hold Glyph IDs.
  • GSUB, cmap 14, glyf, and COLR substitute glyphs.
  • Ligature f + i → fi: Requires a 3rd patch for fi under (f AND i).

Here's the core problem of glyph segmentation: patch activation conditions are evaluated against Unicode codepoints and feature tags, whereas outline patches store Glyph IDs. Because of OpenType layout substitutions like the classic f + i -> fi ligature, placing f and i in separate patches requires a third patch for fi guarded by the conjunctive condition (f AND i).

The Closure Requirement

  • Segment (si): Atomic set of Unicode codepoints and/or feature tags.
  • Initial Font (s0): Baseline glyphs included in the initial WOFF2 font.
  • Disjoint Patches: Every glyph outside s0 belongs to exactly one patch.

Closure Invariant

For any subset D:  Glyphs(s0) ∪ ⋃ci(D) = true Glyphs(pi)  ⊇  closure(Font, D)

Every segmentation plan must uphold two invariants: first, glyph patches are strictly disjoint so we never duplicate glyph outlines across patches; second, it must satisfy the Closure Requirement—for any combination of codepoints and features, the loaded patches must be a superset of the HarfBuzz subsetter glyph closure for that subset definition.

High-Level Segmenting Algorithm

  1. Initialize: 1 segment per codepoint/feature (pre-grouping rare tail in 4s).
  2. Extract Conditions: Assign each glyph a normalized CNF condition.
  3. Initial Patches: Group glyphs with identical conditions into patches.
  4. Initial Font Merging: Move high-probability & fallback glyphs to s0.
  5. Iterative Merging: Merge segments/patches to minimize cost & meet min_group_size.

Implemented in ClosureGlyphSegmenter::CodepointToGlyphSegments. We start with the finest possible segmentation (one segment per codepoint and feature), extract exact glyph activation conditions, group glyphs with identical conditions into initial patches, merge high-probability patches into the initial font, and iteratively merge segments and patches guided by our cost function.

Condition Analysis Modes

1. Subsetter Closure (Legacy)

  • I = closure(s0 ∪ si) ∖ closure(s0)
  • D = closure(All) ∖ closure(All ∖ si)
  • Exclusive: D ∩ I  ·  AND: D ∖ I  ·  OR: I ∖ D
  • Slow O(n) closures; misses composites.

2. Dependency Graph (Default)

  • Single phased Tarjan SCC pass.
  • Exact CNF: (s1 ∨ s2) ∧ (s3 ∨ s4).
  • Fast incremental invalidation on merges.
  • Q1 Simplify: Reduces to pure AND/OR.

Originally, we inferred glyph conditions by treating HarfBuzz's subsetter closure as a black box—computing the full closure A, the closure without segment si (B), and the isolated closure of si (I). Today, our default approach is DEP_GRAPH_ONLY, which builds an explicit dependency graph directly from the font's tables.

Dependency Graph: Node Types

  • Unifies Segment, Unicode (canonical decomp/comp & bidi), Feature, and Glyph dependencies into one directed graph.

The DependencyGraph class unifies four types of nodes into one graph: Segment nodes act as the entry points; they point to Unicode Codepoint nodes and Feature nodes. Codepoint nodes have edges to other codepoints (modeling Unicode canonical decomposition, composition, and bidi mirroring) and to Glyph nodes via cmap and cmap 14 UVS subtables. Finally, Glyph nodes have outgoing edges to other glyphs derived from GSUB, COLR, MATH, and glyf composite references.

Edge Types & Initial Font Folding

Disjunctive Edges

  • u → v: u alone requires v (cmap, glyf, COLR, default GSUB).

Initial Font Folding

  • Nodes in s0 are True and stripped from contexts C.
  • If i ∈ s0, f → fi (ctx: {i}) becomes f → fi!

Conjunctive Edges

  • u —(C)→ v: Requires u AND all of context C:
    • Ligature: f → fi (ctx: {i})
    • UVS: a → a.alt (ctx: {VS1})
    • Feature: a → a.sc (ctx: {smcp})

Edges in the dependency graph come in two flavors: disjunctive edges (u → v, meaning u alone triggers v) and conjunctive edges (u → v with a context set C of required features, codepoints, or glyphs). Anything already in the initial font is folded out of all context sets immediately.

Graph Traversal & Closure Phasing

Two Traversal Modes

  • Enforced Context: Traverses u —(C)→ v only when u and all of C are reached (matches HarfBuzz closure).
  • Non-Enforced Context: Ignores C; finds all reachable glyphs for incremental updates.

Strict Closure Phasing

  1. Segment → Codepoint/Feature + Unicode closure
  2. cmap nominal & cmap 14 UVS
  3. GSUB lookups & MATH / COLR
  4. glyf composite components

Prevents glyf components from falsely triggering GSUB.

A critical subtlety of OpenType subsetting is that HarfBuzz's glyph closure is phased: composite glyphs in the glyf table pull in their component glyphs *after* GSUB substitutions have finished, so a component glyph pulled in by a composite won't itself trigger new GSUB rules. Our dependency graph mirrors this exact phasing.

Condition Extraction via Tarjan's SCC

  1. Initialize: s0 nodes → True; Segment nodes si → exclusive(s_i).
  2. Find SCCs: Run Tarjan's SCC algorithm on the active phase subgraph to emit components in topological order.
  3. Propagate Conditions:
    • Single-Node SCC (|C| = 1): Join edge contexts via And(), join incoming edges via Or(), and normalize to CNF.
    • Multi-Node SCC (|C| > 1, cyclic GSUB): Iterate And/Or propagation around the cycle until reaching a fixed point.

Within each closure phase, we run Tarjan's Strongly Connected Components algorithm, which emits SCCs in topological order. For single-node SCCs, we compute its condition once by joining its parents' conditions. If a font has cycles in its GSUB rules (a multi-node SCC), we iterate around the SCC until the boolean conditions reach a fixed point.

CNF Condition Normalization

Canonical Monotonic CNF:  C = (s1,1 ∨ s1,2 ∨ …) ∧ (s2,1 ∨ s2,2 ∨ …) ∧ …

Clause Subsumption

  • Drops any clause Cj where Ci ⊆ Cj:
    (s1) ∧ (s1 ∨ s2)  ⇒  (s1)
  • Sorted for canonical hashing & equality.

Factoring & Simplification

  • Or(A, B) Factoring: Extracts shared clauses I before cross-multiplying:
    (I ∧ A′) ∨ (I ∧ B′) = I ∧ (A′ ∨ B′)
  • NonCompositeSuperset(): Reduces to pure AND or OR.

We represent every ActivationCondition in monotonic Conjunctive Normal Form (CNF) and simplify via clause subsumption: if clause A is a subset of clause B, B is redundant and dropped. When computing Or(A, B), we avoid exponential blowup by factoring out identical clauses shared between A and B in a single linear pass before taking the cross product of the remaining clauses.

Part 3: Cost-Based Merging & Multi-Script Optimization

Minimizing expected bytes transferred across languages

Once we have our initial fine-grained patches and their normalized CNF conditions, we enter Part 3: the cost-based merger.

Why Merge Segments & Patches?

1 segment per codepoint yields thousands of tiny patches.

  • Per-Patch Overhead (k) vs.
  • Over-Fetching Unneeded Glyphs

Pros vs. Cons

  • Fewer Requests: Saves HTTP/framing overhead.
  • Better Brotli: Shared outline patterns compress together.
  • Smaller Patch Maps: Fewer IFT /IFTX entries.
  • Risk: Merging rare + common glyphs wastes bandwidth!

If we leave one segment per codepoint, the client pays a per-request network overhead on every patch and loses cross-glyph Brotli compression synergy. On the other hand, merging a rare character with a common character like 'e' forces every user to download the rare glyph. We need a quantitative objective function to evaluate candidate merges.

The Segmentation Cost Function

Expected bytes transferred for a random page view:

cost(S)  =  size(Finit)  +  ∑i=1..n P(ci) × (size(pi) + k)

  • P(ci) ∈ [0, 1]: Probability condition ci is triggered on a random page.
  • size(pi): Brotli-compressed byte size of patch pi (captures outline synergy).
  • k = 200 bytes: Fixed network overhead per patch request.

Our cost function is the expected number of bytes transferred per page view. Each patch pi contributes its activation probability P(ci) multiplied by its Brotli-compressed byte size plus a fixed per-request network overhead k (200 bytes by default).

Assessing Candidate Merges (Δcost)

Δcost  =  ∑p ∈ Added ∪ Mod P(c′p)(size(p′) + k)  −  ∑p ∈ Removed ∪ Mod P(cp)(size(p) + k)

Localized Effects

  • Combines exclusive patches.
  • Moves interaction glyphs between patches.
  • Updates segment IDs in CNF clauses.

Greedy Merge Loop

  • Find touched patches via inverted index.
  • Pick pair with lowest Δcost < 0.
  • Repeat until no Δcost < 0 remains.

Because total cost is a sum over independent patches, we use an inverted index (TriggeringSegmentToConditions) to find only the patches touched by a candidate merge, subtract their old cost contribution, and add back their new cost contribution. Any merge with Δcost < 0 reduces expected network transfer.

Segment Merging vs. Patch Merging

1. Segment Merge

  • sa ∪ sb → sab: Unions input segments and updates conditions.
  • {f} + {i}: Collapses {f}, {i}, {fi} into one exclusive patch {f, i, fi}!
  • Best for exclusive patches & folding ligatures.

2. Patch Merge

  • p1 ∪ p2 → p12: Directly unions two patches with Or(c1, c2).
  • {f} + {i}: Forms {f, i} under (f OR i); leaves {fi} untouched!
  • Best for non-exclusive patches.

A Segment Merge unions the underlying Unicode segments sa and sb, which automatically folds conjunctive interaction glyphs like fi into the merged patch. A Patch Merge leaves the input segments alone and directly unions two glyph patches while OR-ing their activation conditions.

Initial Font Merging (s0)

Why Merge into Initial Font?

  • Near-100% probability glyphs waste patch overhead k and a round trip.
  • Moving si into s0 simplifies downstream conjunctive conditions.

Threshold & Fallback

  • Tests segments above probability cutoff (25%–60%).
  • Accepts move if Δcostinit < −0.8k (−160 B).
  • Unmapped/fallback glyphs default to s0.

Before running pairwise patch merging, Merger::MoveSegmentsToInitFont evaluates segments above the probability threshold by comparing the initial WOFF2 font growth against eliminated patch transfer costs. If the net savings exceeds 80% of a network request (-160 bytes), the segment moves into the initial font.

Estimating Condition Probabilities

1. Unigrams (Quality 1–2)

  • Single-codepoint P(a); assumes independence:
    P(∨ ai) = 1 − ∏ (1 − P(ai))
  • Pros: Fast O(k); 1.5 MB dataset.
  • Cons: Overestimates unions P(a ∪ b) on correlated text.

2. Bigrams (Quality 3–7)

  • Pairwise co-occurrence P(a ∩ b) (696 MB dataset).
  • Captures correlation (e.g., q+u, Kanji pairs).
  • Computes tight Bounds [Pmin, Pmax] for k ≥ 3!

Unigram mode uses individual codepoint probabilities and assumes statistical independence—which is fast, but overestimates union probabilities because characters on web pages co-occur. Bigram mode (Q3–Q7) uses pairwise co-occurrence counts P(a ∩ b) to compute rigorous upper and lower probability bounds without assuming independence.

Bigram Probability Bounds

Let S1 = ∑ P(ai),  S2 = ∑i<j P(ai ∩ aj), and k* = ⌊2S2 / S1⌋ + 1:

1. Unions (Dawson–Sankoff)

  • Lower (Pmin):
    [2/(k*+1)] S1 − [2/(k*(k*+1))] S2
  • Upper (Pmax):
    min(1.0,  S1 − (2/n) S2)

2. Intersections (Fréchet)

  • Lower: max(0, ∑ Pmin(Cj) − (m−1))
  • Upper: minj Pmax(Cj)
  • Midpoint: P(ci) = ½(Pmin + Pmax)

For a union of codepoints, we compute the sum of single probabilities S1 and pairwise probabilities S2, and plug them into Formulas 3 and 4 from Kwerel (1975) / Dawson–Sankoff, which give the provably tightest lower and upper bounds using degree-2 marginals. For conjunctions across clauses, we use Fréchet bounds and take the midpoint.

Multi-Script Fonts & Merge Group Isolation

Challenges

  • No Cross-Script Bigrams: Pair counts are collected per script.
  • Shared Codepoints: CJK languages share Han ideographs at different frequencies.

Design Principles

  • Equal Script Weighting: Every script weighted equally (no global traffic bias).
  • Isolated Merge Groups: Disjoint scripts merge independently, bounding O(n2) search.

When encoding a multi-script font, every supported script is treated with equal importance rather than weighting by global internet traffic. We isolate disjoint scripts into separate Merge Groups, which both prevents cross-script merges and shrinks the quadratic O(n2) search space.

Multi-Dataset Cost & Pagg Factoring

Unweighted sum across M profiles in a group (e.g. M = 4 for CJK):

cost(S)  =  ∑m=1..M ∑pi ∈ S Pm(ci) × (size(pi) + k)

Linearity Optimization

  • size(pi) and k are identical across all M datasets:
    ∑m=1..M Pm(ci)(size(pi) + k)  =  (size(pi) + k) × Pagg(ci)
  • Summing Pagg(ci) = ∑ Pm(ci) first avoids M× redundant patch size lookups!

Inside a multi-script merge group like CJK (M = 4), a patch's compressed size size(pi) and network overhead k do not depend on the language dataset. By factoring (size(pi) + k) out of the sum, we sum the condition probabilities across the M calculators to get Pagg(ci) and multiply by the patch size once.

Prioritizing a Primary Script

1. Scoped Initial Font

  • Only the primary script's profile sets initial_font_merge_threshold.
  • Secondary scripts never force glyphs into s0.

2. Cluster Splitting

  • Splits CJK into two disjoint groups:
    1. Primary (Japanese): 100% Japanese weights.
    2. Secondary (Hans+Hant+Korean): Remaining CJK codepoints.

When a user explicitly specifies a primary script like Script_japanese on a CJK font, only the Japanese profile is allowed to move glyphs into the initial font, and AutoSegmenterConfig splits the CJK cluster into two disjoint groups: one covering all codepoints in Japanese, and a second for the remaining CJK codepoints.

Minimum Group Sizes & Heuristic Fallback

Minimum Group Size (Privacy)

  • Enforces min_group_size = 4 per clause:
    minCk ∈ C |Ck| ≥ 4
  • Phase A: Greedily apply Δcost < 0 merges.
  • Phase B: Accept least-positive Δcost merges until ≥ 4.

Heuristic Merger (Fallback)

  • For symbols/PUA without frequency data.
  • Pre-groups in blocks of 3 × min_group_size = 12.
  • Merges adjacent patches in codepoint order up to min_patch_size = 2500 B.

To prevent single-character fingerprinting, our cost merger runs in two phases: Phase A performs all merges with negative Δcost; Phase B allows least-positive Δcost merges for any remaining patches with effective group size below 4. Uncovered codepoints use a fast heuristic merger targeting min_patch_size = 2500 bytes.

Part 4: Key Optimization Techniques & Validation

Pruning O(n2) Brotli evaluations, inert segments, caching & closure verification

Now let's examine Part 4: the algorithmic optimizations that make cost-based segmentation fast in practice, followed by how we validate the final segmentation plan.

Bottleneck: O(n2) Compressions

CJK fonts start with n > 20,000 segments → O(n2) candidate pairs.

Four Optimization Pillars

  1. Best-Case Pruning: Reject pairs before calling Brotli.
  2. Pre-Grouping & Cutoff: Shrink n upfront; skip rare tail.
  3. Inert Segments & Partial Graph: Bypass closure when safe.
  4. Caching & Brotli Tiers: Memoize sizes, closures & probs.

Evaluating C(n, 2) pairs on a 20,000-codepoint font would naively require hundreds of millions of Brotli compressions. To make segmentation practical across the Google Fonts corpus, we combine four key optimization pillars.

Opt 1: Best-Case Cost Pruning

sizebest(A ∪ B)  =  max(size(A), size(B))  +  fbest × min(size(A), size(B))  +  header

Size Reduction Bound

  • Theoretical (fbest = 0): 0 extra bytes for smaller patch.
  • Empirical (fbest = 0.5): 99.8% of pairs retain ≥ 50% of min(size(A), size(B)).

Early Rejection

  • Plug sizebest(A ∪ B) into Δcost.
  • If Δcostbest ≥ 0 (or ≥ best Δcost), skip Brotli!

Before invoking Brotli on a candidate merge of patches A and B, we compute the smallest plausible merged size. Empirically, across real fonts at Brotli 9, 99.8% of pairs retain at least 50% of the smaller patch's compressed size (best_case_size_reduction_fraction = 0.5). If even that best-case size cannot beat our current best Δcost, we skip Brotli entirely.

Opt 2: Pre-Grouping & Tail Cutoff

1. Pre-Closure Grouping

  • Sorts segments by descending P(si).
  • Pre-merges tail segments below 0.05%–5% into groups of 4 before closure.
  • Cuts initial n by up to 4×!

2. Optimization Cutoff

  • Ranks segments by baseline cost P(si)(size(pi) + k).
  • Marks bottom 0.5%–5% cumulative cost tail as cutoff.
  • Skips O(n2) search on cutoff segments; merges in O(1)!

We exploit the Zipfian distribution of character frequencies in two ways: first, PreGroupSegments merges rare segments into chunks of 4 before building the dependency graph; second, segments in the bottom 0.5% to 5% of total cost contribution skip O(n2) pair evaluation completely.

Opt 3: Inert Segments & Partial Graph

Inert Segments

  • Only exclusive glyphs; zero cross-segment edges.
  • Closed Under Union: Merging yields Ga ∪ Gb with zero closure recomputation.
  • Batch Init Merging: Moves inert segments to s0 in one batch!

Incremental Graph Updates

  • Partial Invalidation: Updates only glyphs reachable from merged segment.
  • Composite Filtering: Restricts 3+-way merges to base_segment_index (~15% faster; 86% on Arabic).

Inert segments only map to exclusive glyphs and have zero multi-segment interactions. Merging two inert segments requires zero condition recomputation, and inert segments can be merged into the initial font in a single batch. When non-inert segments merge, we incrementally update only the reachable subgraph.

Opt 4: Caching & Brotli Quality Tiers

Three Caches

  • PatchSizeCache: GlyphSet → compressed bytes.
  • GlyphClosureCache: SubsetDefinition → GlyphSet.
  • Probability Caches: Vector for P(si) + hash map for clauses.

Brotli Quality Tiers

  • Quality 11 (Q6–Q7): Maximum accuracy.
  • Quality 9 (Q4–Q5): Much faster, near-identical merges.
  • Quality 0 (Q1–Q3): O(1) size estimate via font-wide compression ratio!

We layer three caches across the segmenter: PatchSizeCache, GlyphClosureCache, and per-calculator probability caches. We also tune the Brotli quality used during merge evaluation—from Q11 down to Q9, or Q0 where EstimatedPatchSizeCache estimates patch sizes in O(1) time using the font's overall outline compression ratio.

Closure Requirement Validation

1. Incremental State Check

  • ValidateIncrementalGroupings re-runs condition analysis and grouping from scratch.
  • Asserts incremental state matches full recomputation.

2. Closure & Partition Check

  • ValidateSegmentation: s0 and all Gp are disjoint and union to FullClosure().
  • Complement Closure Check: For each patch Gp and clause Ck:
    closure(F, Sall ∖ Ck) ∩ Gp = ∅

At the end of segmentation, we run two strict validation checks: ValidateIncrementalGroupings recomputes all glyph conditions from scratch and asserts equivalence with the incremental state; ValidateSegmentation verifies disjoint partitioning and runs HarfBuzz closure on the complement set Sall ∖ Ck for every clause Ck to prove no glyph in Gp can be reached when Ck is false.

Part 5: The IFT Compiler

Table-keyed patch graphs, recursive compilation & OpenType table handling

Finally, let's dive into Part 5: the IFT Compiler (ift/encoder/compiler.cc), which takes the SegmentationPlan and compiles the actual WOFF2 initial font and patch files.

The Table-Keyed Patch Graph (DAG)

  • Nodes: Non-outline table subset states (cmap, GSUB, GPOS, design space).
  • Edges: Per-table Brotli shared-dictionary binary diffs (.ift_tk) transitioning A → A ∪ Δ.

In the compiler, table-keyed patches form a Directed Acyclic Graph. Every node in the DAG represents an extended state of the font's non-outline tables (e.g., initial font A, A+B, A+C, A+B+C), and every edge represents extending the font with one or more non-outline segments (typically one segment per script plus one for optional layout features).

Table-Keyed Graph Shape Parameters

1. Jump Ahead

jump_ahead (default 2): adds multi-segment outgoing edges in 1 round trip.

2. Prefetch Lists

use_prefetch_lists (true): encodes jumps as a Format 2 Prefetch List of 1-seg patches—zero extra patch files!

3. Max Depth

max_depth (≤ 2048 patches): caps DAG depth D (floor 3); at D−1, one patch adds all remaining segments.

4. All-Segment Edges

include_all_segment_patches: optional "add all remaining" edge at every node.

If a font has many scripts, a full hypercube of table-keyed patches grows as S · 2S−1. We shape this graph with four parameters in SegmentationPlan: jump_ahead = 2 lets clients add two script segments in a single round trip; use_prefetch_lists = true encodes multi-segment edges by listing single-segment patches in the Format 2 prefetch list; and max_depth caps the depth of the graph so total table-keyed patches stay under 2,048.

Recursive Compilation (Compile)

  1. Glyph Patches (.ift_gk): Slice & Brotli-compress outlines for design space.
  2. Outgoing Edges: Assign 128-bit ID; build 1-seg, prefetch & max_depth jumps.
  3. Patch Maps (EntryGraph): Deduplicate shared sub-conditions into IFT /IFTX.
  4. Node Font: Subset original font to node state and insert IFT /IFTX.
  5. Table Diffs (.ift_tk): Recursively compile target nodes B′ and Brotli-diff B → B′.

Here is the 5-step recursive algorithm in Compiler::Compile. At each node, we generate (or look up in cache) the glyph-keyed patch set for the node's variable design space, enumerate outgoing table-keyed edges, compile Format 2 Patch Map tables using EntryGraph::Optimize(), subset the font to the current node, and recursively compile target nodes to generate Brotli shared-dictionary table-keyed patches.

OpenType Special Handling & Testing

OpenType Requirements

  • Retain GIDs: Sizes maxp for all patches.
  • Long loca: Forces 32-bit offsets.
  • 2-Step gvar: Preserves shared tuples.
  • CFF & WOFF2: Desubroutinizes & round-trips.

Fontations Integration Tests

  • Tested against Rust Fontations IFT Client.
  • Verifies exact cmap, outlines & RTs.
  • Future: GK-only mode & size sorting.

Making table-keyed subsetting and glyph-keyed outline patching work together requires careful OpenType engineering: retaining GIDs, forcing long loca offsets when needed, two-step gvar subsetting so shared tuples stay synchronized, desubroutinizing CFF/CFF2 charstrings, and round-tripping the initial font through WOFF2 before diffing. All of this is verified against the Rust Fontations IFT client.
